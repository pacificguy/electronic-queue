# Описание проекта: «Электронная очередь»

## 1. Цель и проблема

Живая очередь — это классическая точка боли в организациях сферы услуг:
поликлиники, МФЦ, банки, сервисные центры, паспортные столы. Посетители
проводят десятки минут в неопределённости, не понимая, сколько человек впереди
и когда их примут. Администраторы вручную распределяют поток, не имеют
актуальной картины загрузки и не могут собирать статистику по оказанным
услугам. Бумажные талоны теряются, а «живые» очереди провоцируют конфликты и
дополнительные споры о порядке.

**Цель проекта** — создать веб-систему электронной очереди, которая:

- позволяет клиенту удалённо записаться на услугу и получить талон с номером
  и временем;
- даёт администратору инструмент управления услугами, окнами обслуживания и
  очередью в реальном времени;
- снижает время ожидания и делает процесс прозрачным и предсказуемым;
- собирает данные для отчётности (нагрузка, популярные услуги, среднее время
  обслуживания).

**Проблема, которую решает проект:** отсутствие прозрачного, справедливого и
управляемого механизма формирования и отслеживания очереди на услуги.

## 2. Целевая аудитория и роли

Система рассчитана на две основные группы пользователей.

| Роль | Кто это | Что делает в системе |
|------|---------|----------------------|
| **Client** | Посетитель организации | Регистрируется, просматривает каталог услуг, создаёт талон (запись), видит свой номер и статус в очереди, отменяет собственную запись |
| **Admin** | Сотрудник / администратор | Управляет каталогом услуг (создание, редактирование, удаление), просматривает все талоны и очередь, меняет статусы талонов (вызов, обслуживание, завершение), смотрит отчёты |

Дополнительно в перспективе предусмотрена роль **Operator** (оператор окна),
но в рамках текущего релиза она не выделяется — её функции выполняет Admin.

## 3. Основной функционал

### Клиентская часть (Client)
- регистрация и вход по email и паролю;
- просмотр списка доступных услуг с описанием и длительностью;
- создание талона на выбранную услугу;
- просмотр собственных талонов и их статусов;
- отмена своего талона, пока он не начал обслуживаться;
- (расширение) уведомления о приближении очереди.

### Административная часть (Admin)
- CRUD по услугам (название, описание, длительность, признак активности);
- просмотр полной очереди и всех талонов;
- смена статуса талона: `waiting` → `called` → `served` / `cancelled`;
- управление пользователями (просмотр, изменение роли, блокировка);
- отчёты: количество талонов по услугам, по статусам, среднее время ожидания.

### Общее
- аутентификация на основе JWT;
- разграничение доступа по ролям на сервере;
- валидация входных данных и понятные сообщения об ошибках;
- веб-интерфейс, адаптивный и дружелюбный.

## 4. Стек технологий

| Слой | Технология | Обоснование |
|------|-----------|-------------|
| Backend | **Python 3.12 + FastAPI** | быстрая разработка, автодокументация OpenAPI/Swagger, асинхронность, строгая валидация через Pydantic |
| ORM / миграции | **SQLAlchemy + Alembic** | декларативные модели, версионирование схемы БД |
| БД | **PostgreSQL 16** | надёжность, транзакции, поддержка конкурентного доступа |
| Хеширование | **passlib[bcrypt]** | безопасное хранение паролей |
| Аутентификация | **JWT (python-jose)** | stateless-авторизация между UI и API |
| Frontend | **React 18 + Vite** | компонентный UI, быстрая сборка, простое состояние авторизации |
| Роутинг UI | **React Router** | защищённые маршруты по ролям |
| HTTP-клиент | **axios** | перехватчики, автоматическая подстановка токена |
| Контейнеризация | **Docker + docker-compose** | воспроизводимый запуск сервера, БД и UI одной командой |
| UI-сервер | **Nginx** | раздача статики и проксирование API |

## 5. Архитектура

Проект построен по клиент-серверной трёхуровневой схеме и разделён на три
независимых контейнера, объединённых общей Docker-сетью.

```
        Браузер пользователя
                │
                ▼
     ┌───────────────────────┐
     │   UI (React + Nginx)  │  :3000
     │  статика + прокси /api│
     └───────────┬───────────┘
                 │ HTTP (JSON, JWT в заголовке Authorization)
                 ▼
     ┌───────────────────────┐
     │  API (FastAPI/Uvicorn)│  :8000
     │  auth • services      │
     │  tickets • admin      │
     └───────────┬───────────┘
                 │ SQL (async/sync драйвер)
                 ▼
     ┌───────────────────────┐
     │   PostgreSQL 16       │  :5432
     │   volume: pgdata      │
     └───────────────────────┘
```

- **UI** собирается Vite в статику и раздаётся Nginx. Nginx также проксирует
  запросы `/api/*` на контейнер `server`, что избавляет от проблем с CORS.
- **Server** реализует REST API, содержит бизнес-логику, проверяет JWT и роли.
  При старте применяет миграции Alembic и создаёт администратора по умолчанию.
- **DB** хранит данные в именованном volume `pgdata`, поэтому они сохраняются
  между перезапусками.

Все параметры подключения и секреты задаются через переменные окружения
(`DATABASE_URL`, `SECRET_KEY`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` и т.д.), значения
по умолчанию заданы в `docker-compose.yml` и вынесены в `.env.example`.

### Сущности данных

- **User** (`id`, `email`, `full_name`, `hashed_password`, `role`, `is_active`,
  `created_at`) — пользователи и их роли.
- **Service** (`id`, `name`, `description`, `duration_minutes`, `is_active`,
  `created_at`) — каталог услуг, которыми управляет Admin.
- **Ticket** (`id`, `number`, `client_id` → User, `service_id` → Service,
  `status`, `created_at`, `called_at`, `closed_at`) — талоны/записи клиентов.

Связи: `User 1—N Ticket`, `Service 1—N Ticket`. Номер талона формируется
последовательно и уникален в пределах дня.

## 6. Результат

В результате получается работающий MVP: `docker compose up` поднимает БД,
API и UI; пользователь может зарегистрироваться, а администратор — получить
доступ по предустановленным кредам, управлять услугами и очередью. Проект
готов к расширению (уведомления, окна обслуживания, роли операторов, отчёты).
